# 授信排除名单由 alerting 持有，billing 保持只读

## Status

Accepted（2026-10-22 定稿，2026-10-23 复核后补充被否方案）

## Context

余额预警需要先剔除"授信活跃企业"，判定依据是计费库的垫付与核销流水。而计费侧的消费分摊表是消费级大表（本地 240 万行，单企业可达 10⁵ 笔），判定轮次每 15 分钟一次，实时反连接或每轮扫表都不可接受。

与此同时，`codesphere-billing` 与 `codesphere-alerting` 是两个仓库、两条发布线。若名单表落在计费库，alerting 要为一张派生缓存去协调跨仓发布顺序、申请建表与写权限。

## Decision

名单表 `balance_alert_credit_excludes` 建在 **alerting 自己的库**（n9e 库），随 alerting 的 AutoMigrate 升级；刷新是「计费库只读聚合 → alerting 库单事务整份替换」的两段式；15 分钟判定轮次只读 alerting 库，用内存集合过滤候选企业。

**billing 仓库因此保持零改动**：不需要 DDL、不需要新增 GRANT、不需要先发布。

## Considered Options

- **落在计费库**（v1.1 曾如此）：判定轮次可同库反连接，少一次内存过滤。被否——需要 billing 出迁移、授予写权限，并让两个仓库的发布顺序强耦合；而收益仅是把几千行的内存过滤换成一次 SQL join。
- **判定轮次实时跨库 join / 每轮扫分摊表**：名单零延迟，无需物化。被否——违反 G4，且把 15 分钟轮次绑在计费库的慢查询风险上；实测分摊表虽有部分索引可用，但核销表的时间列没有索引，随时可能变成全表扫。
- **名单缓存进进程内存**：最快。被否——重启即丢、多副本各自不一致，且"从未成功刷新"这一状态会失去落点，无法支撑 fail closed。

## Consequences

- 名单存在最长约一天的滞后：首次垫付后最多一天才退出预警池，窗口到期也以最近一次成功刷新为准。需要立即切换时用手动刷新。
- 多副本会各自刷新一遍，数据收敛但计费库读放大 N 倍；替换幂等，因此不引入跨实例锁。
- 必须配套刷新状态（落 alerting 配置项）与 fail closed 语义；漏掉它们，空表就会被当成"无人需要排除"，把全部授信企业拉进预警池。
- alerting 对计费库只需只读权限；这条边界要一直守住，否则"派生缓存"就会悄悄变成两侧共享的业务数据。
