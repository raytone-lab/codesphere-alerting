# 信用核销是独立的第三类排除条件，而非冗余校验

## Status

Accepted（2026-10-23）

## Context

刷新 SQL 有三段 `UNION`：未清垫付债务、窗口内信用垫付、窗口内信用核销。代码注释与 PRD 曾把第三段描述为"冗余保护"——理由是"正常数据下，窗口内有核销必有窗口内垫付，两个条件合并成两表一致检查"。

这个描述不成立，且危险：它把一段**有实际语义**的排除条件写成了可以被顺手删掉的一致性校验。

反例：某企业最后一次垫付在 180 天前，20 天前做了对账代充（信用核销）把垫付清零。此时"最后垫付"早已超出 90 天窗口，第二段条件不命中；但企业当下仍按信用账期结算，并在窗口内继续产生新垫付。若只按最后垫付起算，它会在对账代充后立刻被拉回预警池，收到"余额不足"的误报。

## Decision

保留 `RECENT_SETTLEMENT` 作为**独立的第三类排除条件**，并把排除期的起算点定义为「最后一次信用垫付或最后一次信用核销中较晚者」。归因优先级为 `OPEN_DEBT` > `RECENT_ADVANCE` > `RECENT_SETTLEMENT`，优先级只决定 `reason` 落哪一个，不决定是否排除。

## Considered Options

- **降级为真冗余**：要求"窗口内核销且窗口内有垫付"同时成立才排除，从而严格等价于垫付条件。被否——会在对账代充后提前放回预警池，产生对刚结清企业的误报；而误报的成本由运营和客户共同承担。
- **完全移除核销分支**：更简单，表也从三路 `UNION` 降到两路。被否——同上的提前放回问题，且已核实本地核销表 24 行全部来自 `ENTERPRISE_CREDIT`，不存在"核销不代表授信"的噪声可依赖。

## Consequences

- 排除期可能长于"最后垫付 + N 天"，最长可到"最后核销 + N 天"。这一条必须写进面向运营的说明，否则"到期了为什么还在名单里"会被当成 bug。
- 核销表的时间列没有索引，第三段条件是刷新查询里最可能先劣化的一环；已记录为需要 DBA 以 `CREATE INDEX CONCURRENTLY` 在计费库补索引的事项，不进 alerting 迁移。
- 现有 13 条用例没有任何一条覆盖"最后垫付超窗 + 窗口内核销"。新增 TC-14 锁定该行为，防止后续以"精简冗余分支"的名义删掉它。
