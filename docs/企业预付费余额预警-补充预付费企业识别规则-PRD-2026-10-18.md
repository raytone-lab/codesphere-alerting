## 1. 背景

余额预警仅面向预付费企业（余额耗尽即停服）。授信企业由信用额度兜底、另受账期与逾期自动冻结机制管理，进入预警池即产生无效告警。

现行圈选逻辑（PRD v6 FR-01）以信用配置状态为授信判定依据，存在两类已验证的判定缺陷：

1. **配置状态失真（漏报）**：系统现状为信用配置一经创建即恒为 `ACTIVE`，无暂停 / 过期维护动作。配置状态退化为"是否配置过信用"的历史记录，配置过信用但事实已按预付费运营的企业被永久排除出预警池。
2. **资金行为干扰（误报）**：授信企业次月对账完成后由运营经后台代充，代充随即触发 FUNDING 自动核销垫付债务。因此充值流水、钱包余额、垫付是否清零等"当前资金状态"均不能作为客群判定依据。

据此，识别依据调整为：**信用垫付行为记录（只增不改的历史表）+ 时间窗口衰减**。

## 2. 需求目标

| 编号 | 目标 |
| --- | --- |
| G1 | 授信运营企业（含对账代充核销后）不进入预警池 |
| G2 | 事实预付费企业（含授信失效、还清债务后转自主充值）进入预警池 |
| G3 | 客群状态迁移双向自动闭环，不依赖任何人工维护的身份字段 |
| G4 | 圈选过程不实时扫描消费级大表 |

## 3. 定义

| 术语 | 定义 |
| --- | --- |
| 信用垫付 | 消费穿 0 后由信用额度支付的部分，登记于 `balance_consumption_allocations`（`approved_credit_usd > 0`） |
| 未清垫付债务 | `approved_credit_usd - coalesce(settled_usd, 0) > 0.0001` 的垫付记录 |
| 信用核销 | `enterprise_credit_settlements` 中 `debt_source = 'ENTERPRISE_CREDIT'` 的核销；**不含** `NEGATIVE_BALANCE` |
| 授信活跃企业 | 满足任一：存在未清垫付债务；近 N 天内产生过新垫付；近 N 天内有信用核销（N 见 FR-03） |
| 预付费企业 | 活跃企业账户中，非授信活跃的企业（进入余额预警池） |

## 4. 功能需求

### FR-01 预付费企业圈选规则

每轮预警批处理按以下规则圈选目标企业：

```
预警池 = type='enterprise'
       AND status='active'
       AND deleted_at IS NULL
       AND provisioning_quarantined_at IS NULL
       AND NOT 授信活跃
```

参考实现：

```sql
SELECT a.id
FROM billing_accounts a
WHERE a.type = 'enterprise'
  AND a.status = 'active'
  AND a.deleted_at IS NULL
  AND a.provisioning_quarantined_at IS NULL
  AND NOT EXISTS (
      SELECT 1 FROM balance_consumption_allocations al
      WHERE al.billing_account_id = a.id
        AND (
              -- 未清垫付债务
              al.approved_credit_usd - coalesce(al.settled_usd, 0) > 0.0001
              -- 窗口内产生过新垫付；必须先限定 approved_credit_usd > 0，
              -- 否则窗口内任何余额消费都会命中，真预付费被整体误排
           OR (al.approved_credit_usd > 0
               AND al.created_at > now() - make_interval(days => :window_days))
        )
  )
  AND NOT EXISTS (
      SELECT 1 FROM enterprise_credit_settlements s
      WHERE s.billing_account_id = a.id
        AND s.debt_source = 'ENTERPRISE_CREDIT'
        AND s.occurred_at > now() - make_interval(days => :window_days)
  );
```

说明：

- **窗口为滚动 N×24 小时**，不按自然日截断；
- 债务阈值 `0.0001` 对齐计费表 `Decimal(20,12)` 的灰尘量级；不再使用 `> 0`；
- 第二个 `NOT EXISTS` 为冗余保护，覆盖 allocations 极端数据修复场景；正常数据下两表判定结果一致。**必须限定 `debt_source = 'ENTERPRISE_CREDIT'`**：真预付费穿 0 后再充值同样会产生 `NEGATIVE_BALANCE` 核销，不限定会把 TC-05 类企业误排最多一个窗口；
- 不要求 `funding_classification_complete = true`，只认 `approved_credit_usd` 与未清差额，与"垫付事实"口径一致；
- `unapproved_debt_usd`（未批准穿零欠款）本期**不参与**判定；
- `billing_account_credit_configs` 不再参与客群识别，其职责仅为额度与账期管理；
- 判定结果与充值流水、钱包余额、垫付是否已清零无关。

### FR-02 排除名单物化

`balance_consumption_allocations` 为消费级大表（单企业可达 10⁵ 笔），圈选禁止每轮实时执行 FR-01 子查询。要求：

1. 新建物化表，**落在 alerting 自己的库**（n9e 库），随 alerting 升级由 AutoMigrate 建表；计费库只被**只读**查询：

```sql
CREATE TABLE balance_alert_credit_excludes (
    billing_account_id varchar(128) PRIMARY KEY,
    reason             varchar(32) NOT NULL,   -- OPEN_DEBT / RECENT_ADVANCE / RECENT_SETTLEMENT
    refreshed_at       timestamptz NOT NULL DEFAULT now()
);
```

> 归属说明：名单是 alerting 的派生缓存，不是计费业务数据。放在 alerting 库使 billing 保持零改动，也免去为一张缓存协调跨仓发布顺序或授予写权限。

2. **原子替换，禁止空窗**：不得对正式表先 `DELETE` 提交再 `INSERT`。整份替换必须在**单个事务内**完成 `DELETE + INSERT` 一次提交，使 15 分钟判定轮次只会看到"完整旧名单"或"完整新名单"。刷新过程中的空表窗口会把全部授信企业当预付费，直接制造误报。
3. **串行化**：不加跨实例锁。整份替换是幂等的，多副本并发刷最终都会收敛到某一份完整名单，读者始终看到完整快照；加锁只会引入方言分叉和阻塞风险。
4. `reason` 优先级：同一企业多条件命中时只落一行，按 **`OPEN_DEBT` > `RECENT_ADVANCE` > `RECENT_SETTLEMENT`** 取值。
5. **跨库两段式**：刷新先在计费库跑一条只读聚合 SELECT 得到「账户 -> 主因」，再整份替换进 alerting 库。计费库侧不接受任何写入。
6. 预警圈选与"立即跑一轮"只读 alerting 库的名单，用内存集合过滤候选企业；不因手动触发而回扫大表，也不跨库 join。
7. 刷新任务记录每次的名单规模与 `reason` 分布，写入任务日志（供试点期运营核对判定准确性）。

### FR-03 识别窗口参数

| 参数 | 位置 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `credit_advance_window_days` | alerting `balance_alert_settings` | 90 | 授信活跃判定的垫付追溯窗口（天） |

- 默认值依据：授信企业月度对账节奏下垫付产生间隔最长约 31 天，连续 90 天无新垫付即判定运营模式转变；
- **参数设置页可调**：正整数，范围 `1–365`，非法值拒绝保存；
- 生效时机：**下一次排除名单成功刷新**后生效（产品文案可表述为"一般次日"）；
- 修改参数本身不触发扫描大表；需要立即生效时使用 FR-04 的手动刷新。

### FR-04 刷新调度、失败降级与可观测

| 项 | 要求 |
| --- | --- |
| 定时刷新 | 每日 **07:30（Asia/Shanghai）** 全量刷新；本任务显式绑定时区，不依赖进程默认时区 |
| 启动补刷 | 进程启动时若从未成功刷新过，异步补刷一次，避免上线后要等到次日 07:30 才开始圈人；已有成功记录时不做任何事 |
| 与判定轮次关系 | 每 15 分钟判定轮次只读物化表；每日刷新独立执行，二者互不替代 |
| 手动刷新 | 参数设置页提供「刷新排除名单」按钮；成功后展示名单人数与三个 `reason` 的计数摘要；失败返回明确错误 |
| 刷新状态 | 记在 alerting 配置项 `balance_alert_exclude_refresh`（上次成功时间、上次尝试、连续失败数、名单规模与 reason 分布），跨进程重启保留；参数页展示，`GET /api/n9e/balance-alert/exclude-state` 可读 |
| 失败沿用 | 已有上一份成功名单时，刷新失败**沿用旧名单**，不阻断当轮预警 |
| 首次失败 | 从未成功刷新过（表为空且无历史成功记录）时，**当轮不圈人、不发送**（fail closed），并告警；严禁把空表当作"无人需要排除" |
| 连续失败告警 | 连续 ≥2 次刷新失败，经试点钉钉规则告警"排除名单刷新失败，仍在用旧名单"；成功一次即清零计数 |

> 明确禁止的降级方式：清空排除表（全量误报）、回退到 `billing_account_credit_configs` 旧 SQL（两套客群定义并行）、判定轮次实时扫 `balance_consumption_allocations`（违反 G4）。

### FR-05 建表归属、权限与发布顺序

1. `balance_alert_credit_excludes` 与刷新状态均由 **alerting 自己持有**：表随 n9e 库的 AutoMigrate 建立（与 `balance_alert_records` 同一机制），状态落在 `configs` 的 `balance_alert_exclude_refresh`。**billing 零改动**。
2. alerting 对计费库只需要既有 datacenter datasource 的**只读**权限（`SELECT`）；刷新 SQL 不含任何写操作，无需新增 GRANT。
3. 发布顺序不再强耦合：billing 无需先发。alerting 首次启动时表由迁移建好、随后启动补刷一次名单，必然早于下一轮 15 分钟判定。
4. 若表创建失败或刷新失败：按 FR-04 的失败路径处理并告警，**不得**静默回退旧圈选 SQL。

## 5. 验收标准

| 用例 | 前置数据 | 预期判定 | 验收点 |
| --- | --- | --- | --- |
| TC-01 授信运营企业 | 存在未清垫付债务 | 授信活跃，不进预警池 | 代充核销债务清零后，只要 90 天内有新垫付，判定不变 |
| TC-02 授信企业对账代充 | 债务已全部核销，最近垫付 < 90 天 | 授信活跃，不进预警池 | **代充操作前后判定均不得改变** |
| TC-03 授信回归预付费 | 债务清零，最后一次垫付 > 90 天，期间自主充值消费 | 预付费，进预警池 | 余额跌破提醒线时收到预警 |
| TC-04 回归过渡期 | 债务清零，最后一次垫付 45 天前 | 授信活跃，不进预警池 | 满 90 天后自动切换判定 |
| TC-05 真预付费企业 | 从无垫付记录（含穿 0 损耗，穿 0 不登记垫付） | 预付费，进预警池 | — |
| TC-06 新授信未穿 0 | 有信用配置，钱包为正，从无垫付 | 预付费，进预警池 | 首次产生垫付后自动退出预警池 |
| TC-07 个人账户 | `ba_personal_*` | 不进预警池 | 圈选仅限 `type='enterprise'` |
| TC-08 近窗纯余额消费 | 无任何 `approved_credit_usd > 0` 的记录，但窗口内有普通消费分摊 | 预付费，进预警池 | 防止 RECENT_ADVANCE 漏加 `approved_credit_usd > 0` 造成大面积漏报 |
| TC-09 非信用核销 | 穿 0 后充值，产生 `debt_source='NEGATIVE_BALANCE'` 核销，窗口内无信用垫付 | 预付费，进预警池 | 冗余保护不得命中非信用核销 |
| TC-10 首次刷新失败 | 物化表无数据且无成功刷新记录 | 当轮不圈人、不发送 | fail closed，并产生告警 |
| TC-11 刷新中断无空窗 | 刷新过程中并发触发 15 分钟判定 | 只看到完整旧名单或完整新名单 | 不得出现"排除表为空"导致的误报 |
| TC-12 参数边界 | 窗口参数 0 / 366 / 非整数 | 保存被拒绝 | 仅接受 1–365 的正整数 |
| TC-13 计费库只读 | 用只读账号刷新名单 | 刷新成功 | 计费库侧不需要任何 INSERT/UPDATE/DELETE 权限 |

通用验收：

- 圈选不触达 `balance_consumption_allocations`：候选集只查 `billing_accounts`，授信活跃过滤走 alerting 库的名单集合；
- 刷新 SQL 的 allocations 谓词与部分索引 `balance_allocations_account_funding_open_idx` 完全一致，每日刷新走索引扫描而非全表；
- 名单刷新任务幂等，重复执行结果一致；
- 刷新失败不改变上一份成功名单内容；
- 全部用例以自动化测试覆盖。

## 6. 已知局限

| 局限 | 影响 | 处理 |
| --- | --- | --- |
| 季节性停用 > 90 天的授信企业被划入预警池 | 期间产生预警噪音 | 企业恢复消费穿 0 后自动回到授信判定；试点期由运营人工辨别，如噪音显著可调大窗口参数 |
| 授信配置未使用型企业（配置过、从未垫付）进入预警池 | 余额低时产生预警 | 属预期行为：该类企业事实按余额运营，预警提示充值或准备进入授信模式 |
| 名单每日刷新 | 首次垫付后最多约一天才退出预警池；窗口到期也以最近一次成功刷新为准 | 接受；调参或需立即切换时使用手动刷新 |
| 同一企业多条件命中只留一行 | 名单不能反映全部命中原因 | 仅主因入 `reason`；判定结果（是否排除）不受影响 |
| 未批准穿零欠款本期不参与 | 仅有 `unapproved_debt_usd` 的企业仍进预警池 | 试点期观察规模；如确需排除，单独立项 |
