## Problem Statement

排除名单（`balance_alert_credit_excludes`）上线后，"谁在预警池里"这件事已经由代码决定，但关于它的**口径、失败处置和可见性**还有一批没有落地的缺口。分三类人：

**值班工程师**在面对一条"某企业没收到余额预警"的询问时，手上没有可信证据：参数页只显示上次刷新时间，看不出名单规模，也分不清"名单为空"和"从未刷新成功"。启动补刷是异步的，进程在 xx:59 启动时首轮判定会在没有任何告警的情况下静默停圈。若告警总开关当时是关的，失败计数照常累加，"从未成功刷新"的事实会被永久吞掉。手动点刷新失败还会再推一条钉钉到群里——而点按钮的人本来就在页面上。

**企业管理员**在自己的余额告警页可以正常配置阈值和接收人，配置会保存成功，但永远不会收到预警，页面上也没有任何提示。他们唯一的结论是"系统坏了"。

**维护者**面对的是不可信的声明：PRD 写着"全部用例以自动化测试覆盖"，而 TC-01 ~ TC-09、TC-11、TC-13 一条都没有；有一个判定镜像函数没有任何调用方，却让人误以为优先级已被测试锁定。更要紧的是，代码注释和 PRD 都把"窗口内有信用核销"这个分支称作**冗余保护**——这个定性是错的，会导致下一次"精简冗余分支"的重构直接把一段有实际语义的排除条件删掉，让刚做完对账代充的企业立刻被拉回预警池、收到误报。

## Solution

把已经定稿的口径变成可执行、可观测、可被测试锁定的东西，并修掉三处会说谎的地方：

1. **口径纠错**：`RECENT_SETTLEMENT` 由"冗余保护"改为独立的第三类排除条件，排除期起算点明确为「最后一次信用垫付或最后一次信用核销中较晚者」。同步清理代码注释、测试注释与 PRD 中的旧措辞。
2. **失败处置可分**：启动补刷改为在判定 cron 注册之前**同步**完成；补刷失败只记录 + 告警，不阻断进程启动；"从未成功刷新"与"刷新失败但仍在用旧名单"两种情形分别告警，后者只在连续第 2 次报一次并在恢复时补一条；手动刷新失败只在页面回显，不推钉钉。
3. **可见性补齐**：排除名单规模与"本轮命中"并列暴露给运营；被排除的企业在自助页看到客户可读的说明并进入只读状态，转回预付费后自动恢复。
4. **用真库测试锁住口径**：TC-01 ~ TC-14 由连真实 PostgreSQL 的集成测试覆盖，`BALANCEALERT_PG_DSN` 守卫、临时 schema 隔离；同时删掉无调用方的判定镜像函数，并让 PRD 的覆盖声明与事实一致。

## User Stories

### 运营可见性

1. 作为值班工程师，我希望参数页同时显示上次刷新时间、是否就绪、名单规模与三个排除原因的分布，以便一眼判断当前圈人是否可信。

2. 作为值班工程师，我希望"从未成功刷新"以阻断式提示呈现，而不是和"名单为空"长得一样，以便知道当前根本没在圈人。

3. 作为值班工程师，我希望名单规模与"本轮命中"分开显示，以便解释"名单 400 家、本轮只排除 12 家"不是 bug。

4. 作为值班工程师，我希望刷新日志里带上名单规模与三因分布，以便在试点期核对判定准确性而不必查库。

5. 作为值班工程师，我希望手动刷新成功后立即看到名单规模与原因分布，以便当场确认这次调参有没有达到预期。

### 口径与边界

6. 作为值班工程师，我希望窗口内发生的信用核销也能延长排除期，以便对刚完成对账代充的企业不产生误报。

7. 作为值班工程师，我希望看到"排除期可能长于最后垫付 + 窗口天数"这一说明，以便不会把"到期了还在名单里"当成缺陷上报。

8. 作为值班工程师，我希望窗口参数的修改明确在下一次名单刷新后生效，以便知道改完不会立刻改变当轮客群。

9. 作为值班工程师，我希望窗口参数只接受 1–365 的整数、越界直接拒绝保存，以便不会以为改了而实际没变。

10. 作为值班工程师，我希望调用方未提供窗口参数时沿用已存值，以便仍按旧格式调用的脚本不会整体失败。

11. 作为值班工程师，我希望非信用核销（`NEGATIVE_BALANCE`）永远不影响判定，以便真预付费企业穿 0 后充值不会被误排一个窗口。

12. 作为值班工程师，我希望窗口内只有普通余额消费的企业仍留在预警池，以便不会因为漏掉"必须 `approved_credit_usd > 0`"而大面积漏报。

### 失败处置

13. 作为值班工程师，我希望启动时若从未成功刷新过就立即补刷，以便上线当天不必等到次日 07:30 才开始圈人。

14. 作为值班工程师，我希望补刷在判定 cron 注册之前完成，以便进程在 xx:59 启动时首轮判定不会静默停圈。

15. 作为值班工程师，我希望补刷失败时进程继续启动、但明确记录并告警，以便不会为一张派生缓存让整个告警平台起不来。

16. 作为值班工程师，我希望从未成功刷新时无论连续失败多少次都要持续可见，以便整条链路不可用这件事不会被静默。

17. 作为值班工程师，我希望定时刷新连续第 2 次失败时收到一次告警，以便知道名单已经停止更新。

## Implementation Decisions

### 领域口径（不可再议）

- 授信活跃企业 = 满足任一：存在**未清垫付债务**（`approved_credit_usd - coalesce(settled_usd,0) > 0.0001`）；近 N 天内有**信用垫付**；近 N 天内有**信用核销**（`debt_source='ENTERPRISE_CREDIT'`）。三者互相独立，**不得合并或删除**任一支。
- **排除期**起算点 = 最后一次信用垫付与最后一次信用核销中较晚者，长 N 天（`credit_advance_window_days`，默认 90，滚动 N×24 小时）。
- 归因优先级 `OPEN_DEBT` > `RECENT_ADVANCE` > `RECENT_SETTLEMENT`，只决定落哪个 `reason`，不决定是否排除。
- `unapproved_debt_usd` 本期不参与判定；`funding_classification_complete` 不作前置条件；`billing_account_credit_configs` 不参与客群识别。
- 候选集条件固定为 `type='enterprise' AND status='active' AND deleted_at IS NULL AND provisioning_quarantined_at IS NULL`，**两处查询（圈选与自助页定位账户）必须一致**，不得只有一处带隔离条件。

### 模块与接口

- **排除名单刷新**（`balancealert` 包）：`RefreshCreditExcludes` 仍是唯一入口（cron / 启动 / 手动），保证失败计数、状态落库、运营通知只有一处实现。启动补刷改为在判定 cron 注册**之前**同步调用；失败只记录 + 走失败路径，不返回错误、不退出进程。
- **排除名单模型**（`models` 包）：物化表增加 `refreshed_at` 的默认值 `now()`，与 PRD DDL 对齐；刷新状态结构新增 `last_notified_failures`（已通知的失败次数）与 `last_notified_at`（该次失败通知的送达时间），用于区分"故障尚未通知"、"通知已经发出"，以及"已通告的故障是否已被一次成功终止"。
- **设置项**：`credit_advance_window_days` 由值类型改为可空，缺失时沿用已存值，仅显式越界/非整数拒绝；`WindowDays()` 之类取值辅助统一处理默认值。
- **运营接口**：`exclude-state` 增加 `list_total`（名单行数），保留既有字段；名单规模**不**进入判定轮次的 `Stats`（判定轮次不该为日志多读一次配置）。
- **自助接口**：`my-config`、`my-status` 增加 `excluded`（bool）与 `exclude_notice`（客户可读文案，排除态为「当前按信用账期结算，不发送余额预警」，否则为空串）；两接口同源同值。`my-config` 的写入在排除态下拒绝并返回相同文案，不自造新状态码。**不暴露 `reason` 细分类别**。前端接线要求见「Further Notes · 前端交接」。
- **判定轮次**：仍只读 alerting 库名单、在内存过滤；`Stats.Excluded` 语义保持"本轮实际被排除的候选账户数"，与 `list_total` 是两个不同口径。

### 失败通知矩阵

| 情形 | 定时刷新 | 手动刷新 | 页面 | 持续可见性 |
| --- | --- | --- | --- | --- |
| 从未成功刷新 | 每次失败都告警 | 仅页面报错 | 红色阻断提示 | 直到首次成功 |
| 已有成功名单、失败 1 次 | 不告警 | 仅页面报错 | 显示旧名单 + 失败时间 | — |
| 已有成功名单、失败 2 次 | 告警一次 | 仅页面报错 | 同上 | — |
| 已有成功名单、失败 ≥3 次 | 不再告警 | 仅页面报错 | 同上 | 靠页面 |
| 恢复成功（此前已告警） | 发一条恢复通知并清零 | 同左 | 恢复正常 | — |
| 告警总开关关闭 | 不投递，但记入待通知计数 | 同左 | 正常显示 | 开关打开后补报 |
| 告警参数不可读 | 记失败并累加计数，无收件人可发 | 仅页面报错 | 显示 `last_error` | 参数恢复可读后的第一次失败把这段停机一起报出 |

补充两条计数口径（否则矩阵会被"点按钮"和"先恢复又失败"绕开）：

- **手动刷新失败不推进连续失败计数**：只更新 `last_attempt_at` / `last_error`。否则运营连点两次按钮就能把定时任务的计数顶到告警阈值，下一条钉钉会声称"连续失败 3 次"，而实际只有一次定时刷新失败过。
- **补报顺序固定：先还恢复通知，再判失败通知**。"关闭期间恢复、随后又失败"时按次数看仍在故障中，但群里那条"坏了"对应的故障已被那次成功终止；先清账，新故障才有资格按"连续第 2 次"重新排队。判断依据是 `last_notified_at` 与 `last_success_at` 的先后（`last_notified_at` 缺失的旧状态保守认定已结束）。

### 数据与契约细节

- 名单整份替换仍在单事务内 `DELETE + INSERT` 一次提交；不加跨实例锁。
- 刷新顺序：**先提交名单、再写入成功状态**，避免崩溃窗口留下"状态说成功、名单是旧的"。
- `exclude-state` 返回体在既有状态字段基础上新增 `list_total` 与 `ready`。
- `my-config` 写入在排除态返回可读拒绝文案（如"当前按信用账期结算，不发送余额预警，暂不可修改"），不自造新状态码。
- 删除无调用方的判定镜像函数；其优先级语义由真库用例覆盖。
- `reason` 的中文译名只保留运营页一处常量；PRD 只描述语义，不写译名。

## Testing Decisions

**好测试的定义**：只断言外部可观察行为——给计费库一份数据，得到一份名单；给名单与刷新状态，得到"圈了谁 / 是否停圈 / 发了什么";给请求，得到约定的响应字段。不断言 SQL 字符串片段、不断言私有函数、不依赖执行顺序。

**唯一的缝（seam）**：新增一个 **Postgres 真库刷新缝**，在 `ScanCreditExcludes` / `RefreshCreditExcludes` 这一层执行——这是整个特性唯一还没有被执行过的路径。它用 `BALANCEALERT_PG_DSN` 守卫，在同 DSN 内建临时 schema、按计费库表结构最小化建表、跑完 `DROP SCHEMA ... CASCADE`。TC-01 ~ TC-14 全部落在这一条缝上，一条缝覆盖 14 条口径。

真库用例统一以 `TestExclude` 为前缀，本地一条命令 `go test ./balancealert/ -count=1 -run TestExclude -v` 即覆盖全部（含候选集与原子替换）。命名不合前缀的用例会在这个命令下"没跑"，而不是"通过"——这正是本 spec 要消除的假象。TC-06 的 fixture 必须真的插入 `billing_account_credit_configs` 与钱包行，否则它与 TC-05 只是名字不同。

其余一律复用既有缝，不新开：

- **判定轮次**复用 `Runner.run`（fake store + sqlite 的 alerting 库）——覆盖 fail closed、名单过滤、`exclude_blocked`。
- **HTTP 契约**复用 router 层的 httptest 用例——覆盖 `exclude-state.list_total`、`my-config.excluded` 与写入拒绝。

**模块**：排除名单刷新与判定轮次、排除名单模型与状态、运营与自助 HTTP 接口。计费库只作为被测前置数据的来源，不写任何生产代码。

**既有测试资产与缺口**：现有 `exclude_test.go` 覆盖了优先级镜像、状态机、整份替换、fail closed；但它在 sqlite 下运行（`CGO_ENABLED=0`），**无法执行含 `make_interval` 的扫描 SQL**，因此不能作为口径验收依据。现有拦截器式断言（"SQL 里必须包含某段字符串"）只保留"只读、无写操作、索引谓词一致"这三条结构性约束，其余口径断言全部迁移到真库用例。

## Out of Scope

- `billing` 仓库的任何代码改动、迁移或 GRANT 调整。
- 客户自助页的前端源码（不在本仓库，本仓库只提供接口契约与字段）。**该部分必须由前端仓库承接，交接契约见「Further Notes · 前端交接」**——后端字段上线而前端未接线时，Q5/Q16 等效于未实施。
- 为 `enterprise_credit_settlements` 补 `(debt_source, occurred_at)` 索引——这是 DBA 以 `CREATE INDEX CONCURRENTLY` 执行的事项，不进入 alerting 的迁移。

### 前端交接（客户自助页）

本仓库的 `front/` 只有 `statik` 编译产物，**没有自助页源码**。以下契约必须交给前端仓库承接；只交付后端字段等于没做完，因为客户看到的仍是"能配置、永不告警"。

后端将提供（`my-config` 与 `my-status` 两个接口同源同值，避免两页面自相矛盾）：

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `excluded` | bool | 该企业当前是否在授信排除名单内 |
| `exclude_notice` | string | 面向客户的一句话说明；排除态为「当前按信用账期结算，不发送余额预警」，否则为空串 |

前端需要做的：

1. 两个页面都读取 `excluded`，不自行推断（不得用余额、有无阈值、有无接收人反推）。
2. `excluded = true` 时表单整块只读禁用，并在表单上方原样展示 `exclude_notice`；不只是灰掉输入框——需要有一句人能读懂的原因。
3. `excluded = true` 时隐藏或禁用保存按钮，避免提交后才被拒绝。
4. **不得展示 `reason` 细分类别**（`OPEN_DEBT` / `RECENT_ADVANCE` / `RECENT_SETTLEMENT`）：客户侧只允许出现上面的统一文案，内部归因只留在运营页。
5. `excluded = false` 时恢复可编辑，无需任何解锁操作；名单刷新后重新拉取 `my-config` 即生效。

验收（前端侧）：被排除企业的两个页面均显示说明且不可保存；从名单移除后直接刷新页面即恢复可编辑，不出现残留的只读态或缓存中的旧文案。
